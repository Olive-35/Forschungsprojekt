
# MQTT Topic Guide

This document summarizes the MQTT data observed in the JSONL recordings and the meanings described in `FT-MQTT-doc`. It is intended as a compact reference for analysis and anomaly detection.

The "Observed payload data" entries below describe fields and values actually present in the recordings. Event-log inclusion follows the topic filters and event-generation rules in `event_log_creation/mqtt_jsonl_event_log.ipynb` (currently configured for `default_process/Ablauf2.1 08072026.jsonl`); it is not inferred from the topic name alone.

## Topic Layout

```text
/j1/txt/<controller>/...
ccu/<area>/<message>
module/v1/ff/<module-serial>/<message>
fts/v1/ff/<fts-serial>/<message>
```

Each recorded message has the general envelope:

```json
{
  "timestamp": "<capture time>",
  "topic": "<MQTT topic>",
  "payload": { "...": "..." }
}
```

The payload is normally an object. Some CCU order topics contain arrays. The overview captures payload structure; the observed-payload notes below are based on representative messages in the JSONL recording.

## Reading Topics as Business-Process Evidence

Think of an order as the end-to-end job for a workpiece, and of module/FTS messages as evidence about individual steps in that job:

- `ccu/order/request` records the business request to start work; `response` records the CCU's decision/acceptance; `completed` records a terminal outcome.
- `module/.../order` and `fts/.../order` are instructions/plans issued for that job. They show what the CCU asked a resource to do, not that the step actually happened.
- `module/.../state` and selected `fts/.../state` action states provide execution evidence. In the event log, a module command being ordered is distinguished from a module reporting that action as finished.
- An `orderId` links messages to a CCU order. The event-log notebook uses the workpiece ID as the case when it is available, using the CCU response/completed message to resolve an order ID to a workpiece ID when possible. Messages without a resolvable case ID or usable timestamp are omitted.

For event-log timing, the notebook takes an action-level `timestamp` first, then the payload's `timestamp`, then its `ts`, and finally the outer JSONL record timestamp. These are message/action source times when provided; they do **not** prove the exact time a module received a command. The outer timestamp is when the recorder captured the message.

### What the event-log notebook actually includes

The notebook selects these topic patterns, then applies activity-specific rules:

- `ccu/order/request`, `ccu/order/response`, and `ccu/order/completed`: create request, response/acceptance, and terminal-outcome events.
- `module/v1/ff/<serial>/{order,state}` and `module/v1/ff/NodeRed/<serial>/{order,state}`: order messages create selected command-assignment events. State messages create only configured `*_FINISHED` events for the listed DRILL, HBW, AIQS, MILL, and DPS module serials.
- `fts/v1/ff/<serial>/{order,state}`: every route-order message can create `FTS_ORDER_SENT`; state messages create events only for `DOCK`, `PASS`, or `TURN` actions in `FINISHED`, `FAILED`, or `CANCELLED` state.

The notebook does not select `ccu/order/active`, `ccu/order/cancel`, connection/pairing topics, `instantAction`, factsheets, `j1` topics, or CCU state snapshots. A selected message still produces no event if it lacks a resolvable case ID or usable timestamp. Duplicate event candidates may later be consolidated while preserving source-topic provenance.

### `module`: production modules

In process terms, module messages separate a work instruction from evidence of its outcome. `order` means the CCU assigned an action to a station; `state` reports action progress/results. The event-log notebook includes only selected command/state combinations and only creates an event when it can resolve a case ID and timestamp. The wildcard `<serial>` identifies the resource that performed or was assigned the work.

## Common Payload Concepts

- `timestamp` or `ts`: source time associated with a message or action; it is not inherently the time a receiving module got the order. For event-log extraction the notebook prefers `action.timestamp`, then payload `timestamp`, then payload `ts`, and falls back to the outer JSONL record timestamp (capture time).
- `serialNumber`: device identity; useful for grouping and cross-checking messages.
- `orderId` and `orderUpdateId`: link commands, progress updates, and final results.
- `actionState`/`actionStates`: lifecycle/outcome reported for an action. The capture includes `WAITING`, `INITIALIZING`, `RUNNING`, and `FINISHED`; the `NodeRed` branch also contains the misspelling `WAITIING`. A quality failure may appear as `result: FAILED` on a `FINISHED` quality action; the notebook's event lifecycle is the action `state`, so preserve the `result` as outcome detail.
- `loads`/`load`: workpiece or transport load information. The singular/plural difference is protocol-family dependent and should be handled explicitly.
- `errors`: structured error information.
- `factsheet`: relatively static capability information; it should not change frequently.
- `type`, `orderType`, `moduleClass`, `agvClass`, and related fields classify workpieces, orders, modules, or vehicles. Their concrete observed values and locations are listed in the topic rows above.

## Anomaly Detection

Use the topics together rather than analyzing each stream in isolation.

### Connectivity and timing

- Flag missing or unexpectedly delayed `connection` messages.
- Compare `module`/`fts` connection state with `ccu/pairing/state`.
- Learn a normal interval distribution per topic. Flag long gaps, unexpected bursts, or a changed median interval.
- Treat sensor streams differently: camera messages are sub-second, while environmental sensors are approximately minute-scale in these recordings.

### State and action consistency

- Detect invalid action transitions, actions stuck in `WAITING`, `INITIALIZING`, or `RUNNING`, and failed actions without a corresponding error.
- Check that `orderUpdateId` increases consistently for one `orderId`.
- Correlate `ccu/order/request`, `ccu/order/response`, module/FTS `order`, and subsequent `state` messages.
- Compare expected process durations with observed durations and configured production durations.

### Vehicle, inventory, and quality checks

- For FTS, cross-check `driving`, node/edge progress, `waitingForLoadHandling`, battery level, and load state.
- Reconcile `ccu/state/stock` with module `loads` and FTS `load` to find missing, duplicated, or incorrectly located workpieces.
- Monitor battery percentage, voltage, charging state, and the configured charging threshold.
- Track quality-action results, especially unexpected changes in `PASSED`/`FAILED` outcomes.

### Schema and sensor checks

- Detect missing fields, new fields, unexpected nulls, type changes, and undocumented topic branches.
- Handle known schema variants such as `load` versus `loads` and `actionState` versus `actionStates`.
- Detect sensor flatlines, impossible ranges, abrupt changes, or disagreement between related measurements.

## Practical Workflow

1. Group messages by topic and device identifier.
2. For event-log timing, check action-level `timestamp`, then payload `timestamp`, payload `ts`, and finally the outer JSONL timestamp.
3. Build per-topic baselines for message intervals, field presence, state transitions, and process durations.
4. Correlate related records using `serialNumber`, `orderId`, `orderUpdateId`, action IDs, and workpiece IDs.
5. Report anomalies with the topic, device, identifier, timestamp, observed deviation, and related messages.

Some meanings remain implementation-specific: the exact `j1` sensor units, the `f/i` versus `f/o` distinction, `NodeRed` topic segments, and fields such as FTS `lastCode`. These should be treated as unknown dimensions until confirmed experimentally or by the system owner.
